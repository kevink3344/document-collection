# Plan: Append a Unique ID to the Collection Fill URL (Hidden External/Submission ID)

> **Status:** Draft — awaiting review
> **Date:** 2026-08-26
> **Goal:** Append a unique id to the end of a collection's fill URL so it reads like:
> `https://datacollectionportal-sandbox.azurewebsites.net/fill/test-collection-51df3f71?id=12345`
> The id is stored **on the collection** in a hidden field and is captured onto each submission so staff can match a response to an external record.

---

## TL;DR

Today the fill URL is just `${window.location.origin}/fill/${collectionSlug}`. We want to optionally tack a unique id onto it: `...?id=12345`.

- The id is **stored as a hidden collection-level property** (`external_identifier`) — a new column on the `collections` table.
- In the Collection Builder's **Share** tab, the copyable URL becomes `.../fill/<slug>?id=<external_identifier>` when the admin has set one.
- The admin supplies the id value by hand (per your answer: "I will append it manually"). If empty, no `?id=` is appended.
- When a respondent opens the form with `?id=12345` and submits, that id is **captured onto the `collection_responses` row** so staff can relate the submission back to an external system.

This is a small, contained change. It touches one new DB column (plus a migration for SQL Server), the public collection payload, the builder Share tab, the fill page (read the param + send it on submit), and the submit route (persist it).

---

## Clarified semantics (from the review questions)

| Question | Decision |
|----------|----------|
| Where does the `?id=` value come from? | **Admin supplies it manually** (external reference, e.g. an HR or audit record number). Not auto-generated by the system. |
| What happens on submit? | **Capture it onto the submission.** The `?id=` value present in the URL is copied to the `collection_responses` row at submit time. |
| How is it stored on the collection? | **Collection-level column** (`external_identifier`), not a new field type. |

## Understanding the current code

### Fill URL construction (builder)
- `client/src/pages/CollectionBuilderPage.tsx`
  - `copyShareLink()` builds the share link: `${window.location.origin}/fill/${collectionSlug}`.
  - The **Share tab** renders an input bound to that same value (around line 2197) so admins can copy the link.

### Fill page routing & query params
- `client/src/pages/CollectionFillPage.tsx`
  - Reads the slug via `useParams<{slug}>()`.
  - Reads query params via `useSearchParams()`:
    - `isPreview = searchParams.get('preview') === 'true'`
    - `editResponseId = parseInt(searchParams.get('edit') ?? '', 10)` (NaN → null)
  - Calls `getPublicCollection(slug, { preview })` to load the collection.
  - `handleSubmit()` calls `submitResponse(slug, { respondentName, respondentEmail, values })`.

### Collection schema (SQLite/Turso base)
- `server/src/database/schema.ts` — `collections` table (~line 81).
- The `collection_fields` CHECK constraint lists the *visible* field types; a hidden property is **not** one of them (it's a collection attribute, not a form field).

### SQL Server migration path
- `server/src/database/db.ts` — `applySqlServerMigrations()` (~line 1021) has an idempotent `migrations: { name, sql }[]` array, each wrapped in try/catch to ignore "already exists". This is where a new column is added for the `sqlserver` mode.
- The Turso/SQLite path uses the `tableHasColumn()` **ALTER TABLE** pattern in `schema.ts`.

### Submit route
- `server/src/routes/collections.ts`
  - `POST /api/collections/public/:slug/responses` (~line 1590): inserts into `collection_responses`, then inserts `collection_response_values`.
  - The response insert columns are `(collection_id, collection_version_id, respondent_name, respondent_email, editable_until)`.

## Implementation steps

### Step 1 — Add the DB column (both backends)

**SQL Server** (`server/src/database/db.ts`): add one entry to the `migrations` array in `applySqlServerMigrations()`:

```ts
{
  name: 'collections.external_identifier',
  sql: `ALTER TABLE [collections] ADD [external_identifier] NVARCHAR(255) NULL`,
},
```

**Turso/SQLite** (`server/src/database/schema.ts`): add a guarded ALTER TABLE near the other `workflow_definition` / `source_template_collection_id` blocks:

```ts
try {
  if (!tableHasColumn(db, 'collections', 'external_identifier')) {
    db.exec(`ALTER TABLE collections ADD COLUMN external_identifier TEXT`)
  }
} catch (e: any) {
  if (!String(e?.message).includes('duplicate column name')) throw e
}
```

### Step 2 — Expose it through the API payloads

**Server types** (`server/src/routes/collections.ts`):
- Add `external_identifier: string | null` to the `DbCollection` interface.
- `COL_SELECT` already uses `c.*`, so the new column is auto-selected.

**Public/managed collection mapping** (`toApiCollection`, ~line 606): return the new field:

```ts
externalIdentifier: c.external_identifier ?? null,
```

**Request body** (`CollectionBody` + `createCollectionSchema` in `server/src/lib/schemas.ts` + the create/update routes in `collections.ts`):
- Add `externalIdentifier?: string | null` to `CollectionBody`.
- Add `externalIdentifier: z.string().trim().nullable().optional()` to `createCollectionSchema`.
- Add it to the `INSERT INTO collections` column list + params (create, ~line 2061).
- Add it to the `UPDATE collections` SET clause + params (update, ~line 2314).

### Step 3 — Client types & API

**Types** (`client/src/types/index.ts`):
- Add `externalIdentifier?: string | null` to the `Collection` interface.

**API** (`client/src/api/collections.ts`):
- Add `externalIdentifier?: string | null` to `CollectionPayload` so create/update can send it.

### Step 4 — Builder Share tab shows the id in the fill URL

`client/src/pages/CollectionBuilderPage.tsx`:
- `copyShareLink()` and the Share tab input (`${window.location.origin}/fill/${collectionSlug}`) should become:

```ts
const fillUrl = `${window.location.origin}/fill/${collectionSlug}${
  externalIdentifier ? `?id=${encodeURIComponent(externalIdentifier)}` : ''
}`
```

- Add a small "External ID" text input in the Share tab so the admin can type the value manually (this is stored on save via the collection payload). Show a hint: "This id is appended to the fill URL and captured on each submission."

### Step 5 — Fill page reads `?id=` and sends it on submit

`client/src/pages/CollectionFillPage.tsx`:
- Read the param alongside `preview`/`edit`:

```ts
const externalId = searchParams.get('id') ?? null
```

- Pass it into `submitResponse` (and `updateMySubmission`, if editing is surfaced for this id):

```ts
await submitResponse(slug, {
  respondentName,
  respondentEmail,
  externalIdentifier: externalId ?? undefined,
  values: [...],
})
```

> Note: the id is read from the **URL at submit time**, not stored on the client form — it flows through the `?id=` query param each time the form is opened.

### Step 6 — Submit route persists the id onto the response

`server/src/routes/collections.ts` (`POST /public/:slug/responses`):
- Add `externalIdentifier?: string` to the request body type.
- Read the collection's own `external_identifier`: `SELECT ..., external_identifier FROM collections WHERE slug = ?`.
- Add a `collection_external_identifier` (or `external_identifier`) column to `collection_responses` (a new migration) OR just store it. Simplest storage options:
  - **(Recommended)** Add `external_identifier` to `collection_responses` via the same migration pattern, and insert the value:

    ```ts
    INSERT INTO collection_responses
      (collection_id, collection_version_id, respondent_name, respondent_email, editable_until, external_identifier)
    VALUES (?, ?, ?, ?, ?, ?)
    ```

    with `[col.id, col.active_version_id, respondentName, respondentEmail, editableUntil, externalIdentifier ?? null]`.

- Optionally cross-check/sanitize: if the request supplies an `externalIdentifier` that does **not** match the collection's own `external_identifier` (e.g. a stale/copied URL), still persist the supplied value (it's an external reference) or ignore it — decide in review. Default suggested: persist whatever the URL supplied; it is the external reference for that submission.

> **Migration note for `collection_responses.external_identifier`:** add the same idempotent ALTER in BOTH `server/src/database/schema.ts` (Turso) and the `applySqlServerMigrations()` array in `server/src/database/db.ts` (SQL Server).

## Edge cases

| Case | Behavior |
|------|----------|
| **No id set on the collection** | No `?id=` is appended; the fill URL stays exactly as today. Everything backward-compatible. |
| **Admin leaves the External ID blank** | `externalIdentifier` is `null`; URL omits the query param. |
| **Respondent opens URL without `?id=`** | `externalId` is `null`; submission stores a null external id. |
| **Respondent opens URL with a different `?id=`** | The URL-supplied value wins and is persisted (external reference per submission). |
| **Existing collections** | New column is nullable; all existing rows get `NULL` until an admin sets one. No data migration needed. |
| **Encoding** | Use `encodeURIComponent` when building the URL so ids with spaces/special chars are safe. |
| **Draft/preview** | `?id=` is ignored in preview/test submit (no API call), consistent with current preview behavior. |
| **Editing an existing response** | If editing is allowed and the id is fixed per collection, the id is not re-editable on the response — it is captured at first submit. Decide whether to allow re-sending in review. |
